# 个人知识 Wiki 产品需求文档

版本：1.1　　日期：2026-10-14　　状态：待评审

适用范围：桌面端 MVP 及后续扩展边界

上一版本：v1.0（2026-10-14，见 `PRD.md` 与 `output/pdf/个人知识Wiki产品需求文档.pdf`）。本稿在 v1.0 基线上做定向修订，不新增非核心功能范围，保留 v1.0 的数据一致性与错误恢复设计。

本产品面向个人学习场景，将阅读、提问、记录和知识链接放在同一工作流程中。用户在应用内阅读 Markdown 内容，选中陌生概念后获取解释或自行记录，保存时让原文选中位置立即成为指向知识对象的可点击链接。知识对象可按用户习惯显示为便签或独立页面，长期积累为可阅读、可追溯的个人 Wiki。

本产品是一个**独立的桌面 Wiki 应用**，面向个人学习、桌面优先、开箱即用，以完整学习工作流为核心。它不是 Obsidian 插件整合包，也不要求用户先学习一套知识管理方法才能开始使用。

本文用于产品、交互、研发和测试评审。第 2 节列出已确认的产品基线；第 2.2 节列出产品原则；其余章节将讨论中的建议细化为可评审规格，其中优先级、验收细则和补充设计尚不代表已获得产品决策批准。关键待定事项集中列于第 11 节。

## 1 产品背景与目标

### 1.1 背景与问题

个人学习中，阅读陌生概念、向 AI 提问、保存解释和补建链接往往发生在不同位置。解释被保存后，如果无法从原文直接访问，记录就容易成为孤立内容；下次遇到同一概念时，用户仍可能重新搜索或提问。

现有个人知识管理工具普遍要求用户先建立一套方法论：理解库（Vault）概念、双链语法、插件体系和模板结构，之后才能开始记录。这一步门槛与「我想把读到的东西记下来」的原始动机并不匹配，也是本产品要解决的核心问题之一。

本产品以应用内阅读为主要入口，让知识在阅读、提问和理解过程中形成连接。可视化图谱是后续浏览能力，Wiki 链接是首要交互基础。

**产品定位（v1.1 明确）**：本产品是独立的桌面应用，不是 Obsidian 插件整合包。Second Brain Builder 等开源插件是参考对象，其成熟的提示词、AI 调用策略和数据处理方法可以研究，并在许可证允许范围内复用；但不将 Obsidian 插件整体搬入新应用，也不以在 Obsidian 上安装和整合一系列插件作为最终产品目标。产品应具备独立的交互与产品体验。

### 1.2 目标用户与场景

首要用户是产品发起者本人，以及具有类似工作方式的个人学习者。产品围绕持续阅读技术文章、整理学习笔记、理解并复用概念的场景设计；首版按单用户知识库规划。

- 阅读导入的文章时，选中陌生词，查看解释并保存为可点击的知识链接。
- 在已有笔记中记录自己的理解，手动创建或关联知识对象。
- 再次遇到已记录的概念时复用已有对象，并根据新语境补充内容。
- 从某个知识对象查看引用它的笔记，回到最初学习时的上下文。
- 首次安装、没有任何既有知识库和 AI 配置时，也能直接创建或导入一篇笔记并完成一次建链。

### 1.3 产品目标

G01 降低阅读中记录和关联知识的操作成本，保存后不再要求用户另行回到原文手工补链。

G02 让同一知识对象可持续编辑和复用，切换展示形式不产生内容副本或丢失关系。

G03 以桌面本地使用为优先，基础知识库能力不依赖自建服务器；支持离线阅读、编辑和手动建链。

G04 保持 Markdown 内容的可读性与可迁移性，数据可备份，知识来源可以回溯。

**G05 开箱即用与低学习成本**：通过合理默认值、上下文操作和渐进式功能展示，让首次使用者无需学习 Markdown Wiki 语法及复杂插件配置，即可完成创建、阅读、保存和知识关联。用户不应该为了建立自己的知识 Wiki，先去学习一套复杂的知识管理软件。

G05 的具体含义不低于以下几条：

- 首次打开应用即可创建和阅读笔记，不需要先理解 Vault、双链语法、插件和模板概念。
- 基础 Wiki 功能不需要登录、不需要安装命令行工具、不需要配置模型。
- 提供合理的默认设置，复杂配置放到高级选项。
- AI 可以独立启用，启用或停用都不影响已经建立的知识库。
- 日常操作尽量在原阅读位置完成，而不是频繁跳转页面、填写表单。

### 1.4 本期不承诺的能力

建议首版不纳入多人协作、账号体系、云端同步、移动客户端、自动语义推理、GraphRAG、向量检索和全局图谱可视化。完整浏览器剪藏插件与 Web 版保留为后续扩展。上述内容不影响未来方向，但不能作为桌面 MVP 的前置依赖。

**个人学习 Wiki 的边界（v1.1 新增）**：本产品当前不做任意领域的知识库自动构建。具体而言，不承诺自动解析游戏源码和素材、不承诺汇总游戏机制、不承诺解决不同版本之间的知识冲突，也不承诺自动从互联网调查出一套权威的领域 Wiki。

这不限制用户在应用里记录游戏知识。用户仍然可以把《群星》的游戏机制整理成自己的学习笔记，并手动建立链接。区别在于：**当前产品只负责帮助用户理解、记录和连接自己接触到的知识，而不是替用户完成任意领域的完整知识调查。** 此条写入非目标，用于避免未来需求边界不断扩大。

## 2 已确认的产品基线

下表仅记录用户在对话中明确表达或确认的方向。C 编号用于后续需求追溯。

| 编号 | 确认内容 | 对产品的约束 |
| --- | --- | --- |
| C01 | 目标是个人学习知识库和个人知识 Wiki | 以知识内容和内部链接组织体验 |
| C02 | 主要在应用内阅读 | 采集内容进入应用后，能在正文中继续学习与建链 |
| C03 | 支持外部导入，以及内部创建和粘贴文本 | 内容入口不能只依赖 AI 生成 |
| C04 | Markdown 作为通用内容形式 | 阅读、编辑、导入和导出围绕 Markdown 设计 |
| C05 | 便签和独立笔记是同一知识对象的两种视图 | 用户可自由选择；不按字数强制切换 |
| C06 | 内容类型与展示形式分开 | “概念或文章”不能与“便签或页面”共用一个分类字段 |
| C07 | 桌面产品优先，Web 也在考虑范围内 | 先服务桌面使用，Web 不要求首版同时交付 |
| C08 | 保存后原词立即成为可点击的知识链接，是最核心需求 | “保存知识并完成原位建链”是核心验收路径 |
| C09 | 知识在阅读、提问和理解中自然形成连接 | 不要求先完成分类整理才能开始使用 |
| C10 | 产品以独立桌面应用为目标，借鉴已有成熟笔记工具和开源项目的功能实现，但不依赖 Obsidian 运行环境 | 优先复用通用能力，不以兼容 Obsidian 插件生态为设计目标；影响技术选型、产品交互和第三方代码复用方式 |
| C11 | 默认保存并建链，但用户可以选择只保存、手动修改链接目标，或者取消链接 | 用户对知识的控制权需覆盖 AI 生成、知识关联、自动整理和内容修改等全部功能 |
| C12 | 当前不做任意领域的知识库自动构建 | 产品只帮助用户理解、记录和连接自己接触到的知识；边界写入非目标 |

### 2.1 后续规格的标识

“讨论建议”表示原对话中由助理提出、但未被用户逐项确认的方案。“补充设计”表示为形成可执行需求而增加的异常规则、验证方法或发布条件。两者均需在评审中确认，不应被视为用户原话。

直接改写 Markdown、默认点击先预览、稳定 ID 的具体编码、技术栈及首版操作系统，均不属于已确认基线。本文给出推荐方向，并保留明确的决策入口。

### 2.2 产品原则（v1.1 新增）

以下原则用于约束后续全部功能设计，包括 AI 生成、知识关联、自动整理和内容修改。

| 编号 | 原则 | 落地约束 |
| --- | --- | --- |
| PR01 | 用户对知识的控制权 | 任何自动或 AI 行为都必须可被用户查看、修改、拒绝或撤销；默认建议不等于强制执行；不引入强制改变所有用户行为的全局开关 |
| PR02 | 保存即建链是默认，不是唯一 | 保存知识时保留「保存并建链」「仅保存」以及修改链接目标的选择，并记住用户习惯 |
| PR03 | 来源与可信度可区分 | 原文事实、AI 解释和用户自己的理解允许分别保留，不强制三段式模板，但不混淆来源性质 |
| PR04 | AI 只是辅助 | 离线、无 AI 配置、AI 失败三种情形下，基础 Wiki 能力完整可用 |
| PR05 | 渐进式复杂度 | 默认界面只呈现完成学习闭环所需的操作；高级配置与高级模式收拢到明确的进阶入口 |
| PR06 | 原阅读位置优先 | 能就地完成的操作不跳转页面；跳转后返回时保留原阅读位置和上下文 |

## 3 产品范围与优先级

### 3.1 优先级定义

P0 为建议纳入桌面 MVP 的能力；P1 为验证核心流程后补充的能力；P2 为长期探索。优先级是本次整理形成的版本规划建议，不是已承诺排期。Wiki 核心可先于 AI 独立交付验证，但完整 MVP 仍包含可选配置的 AI 解释流程。

| 编号 | 能力 | 优先级 | 依据 |
| --- | --- | --- | --- |
| FR01 | 本地知识库与持久化 | P0 | C07，讨论建议 |
| FR02 | Markdown 创建编辑与阅读（含表格、公式、代码高亮） | P0 | C02、C04 |
| FR03 | Markdown 导入与文本粘贴 | P0 | C03、C04 |
| FR04 | 统一知识对象与两种视图 | P0 | C05、C06 |
| FR05 | Wiki 链接与反向引用 | P0 | C01、C08，讨论建议 |
| FR06 | 选词创建或复用并原位建链（含仅保存与取消建链） | P0 | C08、C09、C11 |
| FR07 | AI 解释与保存（含双入口接入与提示词模式） | P0 | C09、C11，讨论建议 |
| FR08 | 来源保存与上下文回溯 | P0 | C03，讨论建议 |
| FR09 | 搜索与已有知识选择 | P0 | 讨论建议 |
| FR10 | 导出备份与索引恢复 | P0 | C04、C07，讨论建议 |
| FR11 | 网页内容采集最小版本（粘贴富文本转换或 URL 导入正文，二选一先行） | P0 | C03，讨论建议 |
| FR12 | 完整剪藏插件、关系发现与后续平台扩展 | P1 至 P2 | 讨论建议 |
| FR13 | AI 内容来源区分与可信度要求 | P0 | C11，讨论建议 |

另有两个 P0 级别的非功能要求随 FR02 一并验收：富文本结构化渲染（GFM 表格、行内与块级 LaTeX 数学公式、代码语法高亮）与首次使用成本（见 8.5）。

### 3.2 首版范围的取舍

外部内容入口已被明确提出，因此建议将 Markdown 文件导入与文本粘贴纳入 P0。

**网页内容采集（v1.1 调整）**：v1.0 将网页 URL 提取正文整体划为 P1。考虑到目标用户主要阅读网页技术文章，文章进入知识库的第一步成本偏高会直接影响使用。因此将「网页内容采集」拆开处理：

- 最小版本列入 P0，先实现以下两者之一：**粘贴网页富文本并转换为 Markdown**，或**粘贴 URL 导入正文**。
- 完整的浏览器 Web Clipper 插件、导航抓取与站点适配保留 P1。
- 具体先做哪一种，建议在第一次真实使用测试后决定，不必现在就强行加入全部功能。该判断列为 D08。

富文本、表格、公式和代码高亮的渲染要求（FR02）是阅读质量的下限，不是增强项，随 P0 一并交付。

首版采用普通笔记引用关系即可形成 Wiki，不要求对关系标注“属于、依赖、包含”等语义类型。反向引用属于基础导航，不必等待全局关系图实现。

## 4 核心对象与信息结构

### 4.1 对象定义

知识对象是用户保存并可被内部链接引用的一份内容，正文采用 Markdown。便签和独立页面共享内容、身份及关系，不形成两份独立记录。

知识链接表示内部对象之间的引用。来源表示内容从哪里获得，可以指向内部笔记的选段，也可以记录外部 URL、标题、作者和摘录。来源与知识链接应分别建模，不能用外部 URL 替代内部引用关系。

反向引用由已保存的正向链接计算得到。例如 A 引用 B，B 可显示 A 的引用位置；无需在 B 正文中额外插入一条回链。

### 4.2 字段建议

以下字段结构为讨论建议和补充设计；不限定最终数据库表名或文件格式。

| 对象 | 主要字段 | 规则 |
| --- | --- | --- |
| KnowledgeObject | id、title、body、kind、view、aliases、createdAt、updatedAt | id 稳定；kind 与 view 独立；别名可选 |
| LinkOccurrence | id、sourceId、targetId、displayText、anchor、sourceRevision | 每次引用有独立位置，同一目标可被多次引用 |
| SourceRecord | id、ownerId、sourceNoteId 或 sourceUrl、title、author、quote、context、capturedAt | 缺失作者可留空；摘录与上下文可独立保留 |
| DerivedIndex | 搜索数据、出链、反向引用、标题和别名映射 | 可重建；不得是独有用户数据的唯一保存位置 |

建议 kind 初始支持普通笔记、概念、文章；view 初始支持 sticky、page。枚举值属于实现建议，界面使用中文名称。用户无需填写技术字段即可完成创建。

### 4.3 信息架构建议

桌面主界面由知识库导航、正文阅读编辑区和辅助面板组成。辅助面板承载知识预览、AI 问答或反向引用；具体布局不锁定为固定三栏。设置区域集中管理知识库位置、AI 配置、备份与索引操作。

首版可提供笔记列表、最近使用与搜索入口；不强制用户先建文件夹、设置类型或维护标签。知识对象的默认视图与“从链接打开时如何预览”是两个独立规则。

按 PR05，首屏默认只呈现创建、阅读、选词、保存与搜索；知识库位置、AI 配置、索引维护、高级 Markdown 选项收拢到设置或高级入口。

## 5 核心用户流程

### 5.1 阅读选词并保存知识

1. 用户创建、粘贴或导入一篇 Markdown 笔记，在应用内阅读。
2. 用户选中一个词或短语；系统记录来源对象、选中文本、位置及当前内容版本。
3. 用户选择“问 AI”“创建知识”或“链接已有知识”。未配置 AI 时仍可使用后两条路径。
4. 系统预填目标标题，并沿用用户上次使用的展示形式（便签或独立页面）；存在候选对象时可选择复用。用户可直接接受默认值，也可以修改。
5. 用户执行“保存并建链”（默认）。系统保存目标内容，并让来源中的选中位置成为内部链接。
6. 保存成功后，原阅读位置保持不变；用户可立即打开知识内容，目标对象显示对应反向引用。

**减少强制确认步骤（v1.1）**：v1.0 要求用户在保存前编辑内容、确认标题、选择便签或独立页面。这些操作必须支持，但不一定每次都要求用户手动完成。允许预填标题、记住上次使用的展示形式，并允许用户修改。减少步骤与保留选择权并不矛盾。

**建链方式可由用户选择（v1.1）**：默认保存并建链，用户还可以选择“仅保存”。两种操作的结果不同：

| 操作 | 结果 |
| --- | --- |
| 保存并建链（默认） | 保存知识对象，原文选段变成可点击 Wiki Link |
| 仅保存 | 保存知识对象，不修改原文 |
| 保存并修改链接目标 | 保存知识对象，并把选段链接到用户指定的其他对象 |
| 取消链接 | 不改写原文；已存在的链接按 FR05 的解除引用规则处理 |

建议不在全局设置中强制改变所有人的行为，而是在保存界面直接提供选择，并记住用户习惯。FR04 已很好地处理了便签与页面的自由切换，不需要改动。

验收主例：在《记忆系统》中选中 Scratchpad，自行填写或通过 AI 获得解释，保存后原词可点击。关闭并重新打开应用，目标内容、该链接和引用来源仍可用。

### 5.2 查看并继续阅读

推荐从正文点击内部链接时先显示预览，用户可进一步打开完整页面。关闭预览或返回来源后，保留原阅读位置。预览形式可以与对象默认视图不同，避免把“该对象是便签”与“只能弹窗打开”绑定。默认打开方式列为 D02 待确认项。

### 5.3 复用已有知识

选词后先匹配标题和别名，再允许搜索目标。选择已有对象只新增当前引用；AI 新回答不会自动覆盖旧内容。用户可选择追加、编辑后替换，或不修改目标内容。同名不等于同一知识，最终目标由用户确认。

### 5.4 外部内容进入知识库

全文导入后形成内部 Markdown 对象，用户可在导入正文中选词建链。只保存 URL 和摘录时，它们属于来源记录；可以与内部知识关联，但不承诺修改外部网页或在外部原文上生成应用内链接。

首版优先支持文件导入、粘贴文本，以及 3.2 节确定的最小网页采集方式（粘贴富文本转换或 URL 导入正文，二选一）；完整插件剪藏见 FR11、FR12。

### 5.5 首次使用流程（v1.1 新增）

1. 用户首次打开应用。系统引导用户选择或创建一个本地知识库位置，并提供默认位置建议，不要求注册、登录或配置模型。
2. 用户直接新建笔记，或导入/粘贴一篇 Markdown 内容。系统不要求用户先理解 Vault、双链语法、插件或文件索引概念。
3. 用户在正文中选中一个陌生概念。系统提供“创建知识”“链接已有知识”“问 AI”三个入口；未配置 AI 时前两个入口完整可用。
4. 用户自行填写知识内容（或启用 AI 后获得解释并编辑确认），接受预填标题与默认展示形式，执行“保存并建链”。
5. 原文选段成为可点击的 Wiki Link，目标对象可打开，重启应用后关系仍可用。
6. 用户后续可选择启用 AI：在应用内统一入口完成配置后，继续上述流程；配置过程不影响已建立的知识库。

该流程是 AC13 的操作蓝本。

## 6 功能需求与验收条件

### FR01 本地知识库与持久化

建议用户首次使用时选择或创建本地知识库，无需为基础功能注册账号或部署后端服务。应用展示当前知识库及保存状态。桌面数据应存放在可识别、可备份的位置。

补充设计（v1.1）：首次引导提供建议默认位置，用户接受即可完成初始化；不要求用户先理解目录结构或索引机制。

验收：在无网络、无 AI 配置条件下创建和编辑笔记，关闭应用后重新打开，正文、视图选择和内部链接保持一致。路径不可写时显示原因并保留尚未保存的编辑内容。

### FR02 Markdown 创建编辑与阅读

支持创建、重命名、编辑与阅读 Markdown 对象。知识链接由独立解析规则提供；渲染层与编辑内容使用同一份数据。

**阅读能力要求（v1.1 扩大）**：v1.0 要求覆盖标题、段落、列表、引用、代码块、普通链接和图片引用。这些是下限，不是全部。对真实学习场景，还应覆盖结构化与学术内容：

| 阅读能力 | 优先级 | 说明 |
| --- | --- | --- |
| GFM 表格 | P0 | 必须正确渲染；学习笔记与对比内容大量使用表格 |
| 行内与块级 LaTeX 数学公式 | P0 | 学习 Transformer、机器学习、算法等内容时必需 |
| 代码语法高亮 | P0 | 代码块需按语言高亮，且不得被链接解析或 AI 改写 |
| Mermaid 图表 | P0（条件项） | 是否列为 P0 取决于 AI 输出规范是否包含 Mermaid 代码块 |
| 脚注、任务列表 | P1 | 按需支持 |

若阅读器不能正确呈现上述内容，即使 Wiki 引擎可靠，也会严重影响实际使用。相关证据：参考项目 Second Brain Builder 已证明高质量 AI 生成笔记会包含大量结构化 Markdown，而不只是普通文字；用户最早提供的「记忆系统」示例本身就是一张表格。

补充设计：提供已保存、保存中、保存失败状态；普通文本和代码内容不能被 AI 或链接解析器无故改写。图片引用缺失时保留可修复占位和原引用，不静默删除。未识别的 Markdown 扩展语法应以可读的原文形式降级显示，而不是丢弃内容。

验收：中文、代码块和已有 Markdown 链接在编辑保存后语义不变；重复打开不产生重复标题或元数据；编辑失败不显示成功状态；表格、行内与块级公式、代码高亮在编辑与阅读两种状态下渲染一致；链接解析不改变代码块内文本。

### FR03 Markdown 导入与文本粘贴

支持导入一个或多个 .md 文件，并支持新建对象后粘贴纯文本或 Markdown。导入时给出结果反馈，保留可识别的来源信息。文件重名、对象 ID 冲突和附件处理应有明确提示。

补充设计：默认导入为知识库副本，原始外部文件不被静默覆盖；选择目录作为知识库与导入文件应使用不同操作。普通文本保持原文。网页富文本的转换要求见 FR11。

验收：外部文件导入后可以在应用内阅读并原位建链；同名文件不覆盖已有笔记；不支持的资源或缺失附件在结果中明确列出。

### FR04 统一知识对象与展示切换

创建时允许选择便签或独立页面；两种形式都允许长文本或短文本。用户可随时切换默认视图，内容类型保持独立。

验收：一篇长文本使用便签、一句话使用页面均有效；切换后对象 ID、正文、出链、反向引用和来源记录不变；任一入口编辑后，其他视图显示同一份更新内容。连续创建多个对象时，界面沿用上次选择的展示形式。

### FR05 Wiki 链接与反向引用

支持创建并打开内部链接，在目标对象显示引用它的来源笔记和上下文。推荐使用可读 Wiki Link 表达，并在内部解析到稳定对象 ID；重命名后已有引用应仍指向同一对象。

补充设计：无法唯一解析同名或别名时要求用户选择；目标缺失时显示未解析状态。解除引用只移除关系，不删除目标对象。删除目标时应提示受影响引用，并提供恢复或改链路径。

验收：A 引用 B 后，B 显示 A；从反向引用返回 A 的对应位置。同一段落和多处重复引用可分别定位；重命名 B 后关系不丢失；目标删除后不跳转到另一篇同名笔记。

### FR06 选词创建或复用并原位建链

这是首版核心功能。对选中文本创建新对象或关联已有对象后，当前选中位置立即呈现内部链接。默认只处理当前选择，不批量改写其他同名出现位置。

**用户控制权要求（v1.1 补充）**：默认行为是保存并建链，但用户必须能够自主选择只保存、手动修改链接目标，或者取消链接。选择入口直接出现在保存界面，并记住用户习惯；不引入强制改变所有人行为的全局开关。

讨论建议采用显式写回 Markdown；是否采用独立批注层保留为 D01。无论最终存储方式如何，都应满足原位可点击、重启后有效、可导出恢复的行为要求。

补充设计：空选择不触发建链；首版可限制为单一连续文本片段。已存在链接、代码块内文本或跨多个结构块的选择，不执行破坏性嵌套改写，界面说明原因。保存前校验选段仍与记录版本匹配；不匹配时请用户重新定位。

验收：保存一次即可完成目标保存和原位链接；相同词出现三次时，仅选中的一次变化；重复点击保存不新增重复对象或嵌套链接；取消操作不改写来源正文；选择“仅保存”时原文不被修改，且知识对象可在目标对象中正常阅读和再次引用。

### FR07 AI 解释与保存

用户主动提问时，AI 基于选中文本及必要的附近上下文生成解释，支持继续追问和编辑结果。AI 回答先作为会话内容，只有用户保存后才成为知识对象。保存复用 FR06 流程，不建立另一套 AI 专用笔记系统。

**AI 接入方式（v1.1 新增）**：v1.0 将 AI 提供商与配置方式整体列为 D05。技术上合理，但缺少一条明确的产品要求：**不应强制用户安装 Claude Code、Codex 等命令行工具才能启用 AI。** 至少提供两类入口：

| 模式 | 配置方式 | 适用用户 |
| --- | --- | --- |
| 普通模式 | 在应用内配置受支持的模型 API 服务；未来可直接使用内置云端 AI 服务 | 不希望接触命令行工具的用户 |
| 高级模式 | 连接已有运行环境，例如 Codex、Claude Code、Ollama 等 | 已有本地或第三方 AI 环境的高级用户 |

需要明确的现实约束：API Key 仍然意味着一定程度的配置；内置云端服务涉及服务成本。现阶段不应承诺所有 AI 能力无条件零配置。产品要求是「AI 可以独立启用，且不影响已经建立的知识库」，而不是「AI 无需任何配置」。

**提示词模式（v1.1 新增）**：提示词应经过专门设计。建议内置「简明解释」和「深入理解」两种基础模式，其他模式放到高级功能中。不必一开始就提供大量教学模式，否则容易重新走向 Obsidian 那种选择复杂度。

讨论建议允许分别记录 AI 解释与用户自己的理解（见 D10）。补充设计要求发送前可查看上下文范围；默认不上传整个知识库。API 提供商、模型、密钥保存方式及是否支持本地模型见 D05。

验收：未配置、超时、额度不足或中断时，已编辑笔记和手动建链仍可用；未完成回答不被静默保存；保存到已有对象前必须明确内容变更方式；取消问答不自动生成知识节点；两种提示词模式产出的内容在保存前均可编辑。

### FR08 来源保存与上下文回溯

保存由选词产生的知识时，记录来源对象、原始选段和必要上下文；外部导入内容允许保存原始 URL、标题、作者与采集时间。来源信息与普通知识链接分别展示。

补充设计：对象正文修改后，历史来源摘录仍保留。精确位置无法恢复时，展示摘录并打开来源对象，不声称已定位到原位置；外部网页失效不影响本地已保存知识的阅读。

验收：从知识对象能查看其学习来源；同一对象可有多个来源；重命名来源对象不丢失关系；导出再导入后，来源摘录仍可读取。

### FR09 搜索与已有知识选择

首版建议支持标题、别名和正文关键词检索，并在建链时复用同一搜索能力。结果至少显示标题与内容片段，帮助用户区分同名对象。复杂语义检索不属于首版要求。

验收：编辑保存后结果能更新；可以按标题或别名找到既有目标；有多个候选时不自动合并或随机选择；无结果时可进入创建流程。

### FR10 导出备份与索引恢复

知识库应能整体备份和恢复，包括正文、附件、对象身份、链接关系及独有来源记录。采用本地 Markdown 原件加索引的方案时，索引只是派生数据；不允许将唯一的来源锚点或 ID 绑定只保存在可删除索引中。

建议区分完整备份包和通用 Markdown 导出。前者用于无损恢复；后者面向其他工具，应说明 Wiki Link 扩展和元数据的兼容边界，必要时提供相对路径链接转换。

验收：将备份恢复到新位置后，对象数、正文、附件、关系和来源一致；重建索引不改变用户内容；重建失败不覆盖原件。导出格式及兼容范围见 D03、D04。

### FR11 网页内容采集

**最小版本（P0，v1.1 提升）**：至少支持以下两者之一，用于把网页文章内容带入知识库：

- 粘贴网页富文本，转换为 Markdown 并保留来源；或
- 粘贴 URL，提取正文生成 Markdown 并保留来源。

两者先实现一个即可，具体选择见 D08。提取失败时回退为手动粘贴或来源摘录，不承诺所有网站均可自动导入。

**完整插件（P1）**：浏览器插件优先负责采集全文、选段及来源，并交由应用处理 AI、知识对象和建链。插件内独立 AI 问答保留为探索项，不与桌面 Wiki 核心同时承诺。

验收（最小版本）：从浏览器复制的正文粘贴后保留标题层级、列表、表格与代码块结构；来源记录包含 URL 和采集时间；提取失败时明确提示并允许手动补全，而不是保存空内容。

### FR12 关系发现与平台扩展

P1 可增加未链接提及建议、别名维护、对象合并和局部或全局关系图。建议均由用户确认后生效，不全库自动改写。对象合并需单独设计旧引用迁移和撤销。按 PR01，任何自动整理结果都必须可查看、可拒绝、可撤销。

Web 版可复用核心模型与交互，但浏览器持久化、备份提示和部署方式需单独设计。Web 与桌面共用代码不意味着自动同步；同步、冲突解决、身份认证及加密属于后续独立范围。PDF 解析、语义关系和智能整理暂列 P2。

验收：关系建议以可查看、可拒绝的形式呈现，不自动写入正文；对象合并在执行前展示受影响引用，执行后可以撤销；这些能力不进入 P0 验收范围，缺失时不影响 Wiki 核心可用。

### FR13 AI 内容来源区分与可信度（v1.1 新增）

AI 解释必须与原文事实、用户自己的理解在信息结构上可区分。具体要求：

1. **允许区分而不强制模板**：不要求用户使用三段式笔记模板，但系统应允许保留不同来源的信息。例如：
   - 原文指出 Scratchpad 用于 Agent 的临时状态管理（原文事实）。
   - AI 给出了一个通俗类比（AI 解释）。
   - 用户补充了自己对它与工作记忆关系的理解（用户理解）。
   这三种信息的可靠程度和性质不同，保存后应仍可辨认。
2. **优先依赖原文**：解释某篇论文中新提出的概念时，应让模型优先依据选中文本及必要上下文；如果使用通用知识进行扩展，应与原文内容区分。
3. **避免自信补充原文没有提供的事实**：不允许让 AI 以确定语气补充原文未提供的事实。必要时允许标注不确定性。
4. **不做无依据的结论**：当上下文不足时，AI 应说明信息不足，而不是生成看起来完整但缺乏依据的解释。

这一条也是未来是否支持更复杂领域 Wiki 的基础。

验收：在同一知识对象中，原文摘录、AI 解释和用户补充在保存后仍可区分来源；无依据的补充内容不会被呈现为原文事实；用户可以在保存前删除或改写任一部分。

## 7 数据一致性与异常处理

本节为补充设计，用于保护“保存即建链”的核心行为。实现可采用日志、事务式协调或可恢复操作记录，不预设跨文件操作天然具备数据库事务能力。

### 7.1 保存并建链的一致性

一次操作涉及目标内容、来源引用和派生索引。只有目标与来源均持久化成功，才显示“保存并建链成功”。重复提交应识别为同一操作，避免重复节点和重复链接。

若目标已保存但来源改写失败，提示“知识已保存，链接未完成”，保留可重试入口，不能再次创建相同目标。若仅索引更新失败，应保留已保存的正文和链接，提示索引待修复并支持重建。首次重启应能识别未完成操作并恢复或引导处理。

**与用户选择的关系（v1.1）**：当用户选择“仅保存”时，成功状态只要求目标持久化成功，不应因未写入链接而报错或显示部分失败。当用户选择“保存并建链”时，才适用上述“知识已保存，链接未完成”的可重试状态。系统应按用户实际选择的操作用语，不能把未建链一律描述为异常。

### 7.2 主要异常与预期行为

| 场景 | 预期行为 |
| --- | --- |
| AI 回答期间原文发生变化 | 保存前重新校验选段，不凭旧偏移量覆盖新正文 |
| 外部编辑器同时修改文件 | 检测版本差异，保留两侧内容并引导解决，不静默覆盖 |
| 同名标题或重复别名 | 展示候选，要求选择目标；保留稳定身份 |
| 目标文件或来源文件被删除 | 显示缺失状态，保留关系证据和可用摘录，提供恢复或改链 |
| 磁盘满或目录无写权限 | 保留草稿，明确未保存；恢复条件后可以重试 |
| 索引损坏 | 从完整原始数据重建，重建期间避免显示错误关系为事实 |
| 用户撤销刚才的建链 | 恢复来源选段；复用的既有对象不得随之删除 |
| 用户选择仅保存，随后又想建链 | 允许从知识对象或原文再次发起建链，复用 FR06 流程，不产生重复对象 |
| 导入原文需要恢复 | 保留原始副本或快照；完整版本历史可后续实现 |

### 7.3 身份与 Markdown 的一致性

仅使用标题不能唯一识别对象。最终方案必须说明对象 ID、文件路径、可读链接与同名解析之间的对应关系，并证明这些绑定在导出、恢复和索引重建后仍然成立。

`[[标题]]`、带别名的 Wiki Link、相对路径链接或带 ID 的链接均可作为评审候选。本文不将任何一种语法写成已批准规范。代码实现前完成 D03，可避免后续重命名或迁移时大量断链。

此项为 v1.0 已有的正确设计，v1.1 保留并不因降低 MVP 工作量而删除。

## 8 非功能需求与验证指标

### 8.1 离线可用与可靠性

基础阅读、编辑、搜索、手动建链和浏览已有知识应在离线环境可用；调用云端 AI 和获取外部网页时允许要求联网。成功保存的内容须在正常退出和再次打开后保持一致。异常中断、损坏索引及外部改动应有可验证的恢复路径。

### 8.2 隐私与内容安全

补充设计：默认在本地处理知识库内容。只有用户主动调用 AI 或外部采集时发送必要数据；不后台上传完整知识库。密钥不写入 Markdown、普通导出包或日志。导入 Markdown 中的脚本和危险 HTML 不执行；应用文件读写范围应限定于用户选择的知识库和明确授权的资源。

上述要求用于定义应用行为，不等于对所有 AI 服务的数据处理方式作保证。具体服务及其设置随 D05 确定。

### 8.3 性能与易用性

建议验证集为 1,000 个对象、约 100 MB 文本、10,000 处内部链接；附件大小单独统计。以下为待技术试验确认的目标，不能视为已验证性能或固定发布承诺。

| 操作 | 建议目标 | 测量口径 |
| --- | --- | --- |
| 打开已有本地知识预览 | P95 不超过 300 ms | 索引就绪，记录硬件与冷暖状态 |
| 关键词搜索 | P95 不超过 500 ms | 从提交查询到首批结果出现 |
| 本地保存并建链 | P95 不超过 1 s | 不含 AI 生成和外部网络请求 |
| 重建索引 | 显示进度并可识别失败 | 保留原件；完成后校验关系数量 |
| 渲染含表格、公式与代码高亮的笔记 | P95 不超过 1 s | 1,000 行以内的典型学习笔记 |

核心功能支持键盘操作和明确的焦点反馈。链接、保存失败和缺失目标不能只靠颜色区分。准确性能预算、测试设备和最小系统版本在 D06、D07 中确认。

### 8.4 产品效果评估

试用阶段关注四项数据：首次完成“阅读到建链”的耗时；需要额外手工补链的次数；再次阅读时打开已有知识的次数；因重名、定位或保存失败而中断的次数。建议通过本地记录或用户观察收集，不默认引入云端分析服务。

对照当前手动记录流程验证操作成本是否下降。留存率、活跃人数和商业指标在获得真实使用数据前不设定虚构目标。

### 8.5 首次使用成本（v1.1 新增）

首次使用成本是本产品的重要竞争力，必须像「保存即建链」一样落实为可验证要求，而不只是「界面简洁」的主观判断。

| 指标 | 建议目标 |
| --- | --- |
| 从启动到可编辑笔记 | 不超过 2 次点击，且不需要登录、注册或配置模型 |
| 首次完成「阅读到建链」 | 从打开应用到形成可点击 Wiki Link，不超过 5 个主要步骤 |
| 必填配置项数量 | 基础功能为 0；AI 为独立可选步骤，不构成前置 |
| 首次流程中出现的专业概念 | 不出现必须理解的 Vault、双链语法、插件、模板、索引等术语 |
| 默认值可用率 | 标题、展示形式、知识库位置均可预填并被直接接受 |

同时要求（可靠性指标）：

| 指标 | 建议目标 |
| --- | --- |
| 富文本渲染警告 | 未识别的 Markdown 扩展语法以原文降级显示，不丢失内容 |
| 阅读位置保持 | 从预览或知识页面返回来源时，阅读位置恢复且不产生错误定位 |
| 配置可逆性 | 启用或停用 AI 配置后，已有知识库内容与链接关系不发生变化 |

按 PR05，以上指标以默认界面为准进行测量，不包含用户主动进入高级设置后的操作。

## 9 技术架构建议

本节保留原对话中后期的候选方案，供研发评审；技术选型尚未锁定，也不代表已完成兼容性或打包验证。

### 9.1 分层方案

表现层负责 Markdown 编辑阅读、知识预览、两种对象视图及 AI 面板；共享核心负责对象管理、选择定位、链接解析、来源与索引协调；存储适配层连接本地文件和搜索索引。后续 Web 端可替换存储适配，不将浏览器限制渗入核心模型。

**独立桌面应用前提（v1.1 明确）**：按 C10，架构以独立桌面应用为目标，不依赖 Obsidian 运行环境，不以兼容 Obsidian 插件生态为设计目标。借鉴与复用边界如下：

- **优先复用通用能力**：Markdown 解析与渲染、编辑器内核、全文检索、正文提取等通用组件可以选用成熟开源实现。
- **参考而非照搬**：Second Brain Builder 等插件项目的提示词设计、AI 调用策略和数据处理方法可以研究，并在许可证允许下复用代码或思路。
- **不继承插件运行时**：不要求以宿主应用（Obsidian）的插件 API、库结构或事件模型为前提；对象模型、存储与交互由本产品自行定义。
- **许可证合规**：复用任何第三方代码前确认许可证条款与署名要求，并记录来源，避免后续分发风险。

**AI Provider 适配层（v1.1 新增）**：技术架构中应正式加入 AI Provider 适配层，而不只是笼统写一个 AI 服务。该层负责统一模型与提供商接入、提示词模板管理、上下文裁剪、调用失败与重试、用量与错误记录，以及普通模式与高级模式（本地模型、CLI 运行环境）的统一抽象。AI 不可用时，共享核心和本地持久化继续工作。

| 层次 | 对话中的候选技术 | 评审重点 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 编辑器集成与桌面构建兼容性 |
| 桌面容器 | Tauri 2 | 文件权限、发布平台、安装与升级 |
| 编辑与渲染 | CodeMirror 6、remark、rehype | 选区映射、Wiki Link 扩展、安全渲染；表格、数学公式与代码高亮插件链 |
| 原始数据 | Markdown 与可备份元数据 | 身份、来源、附件和链接完整恢复 |
| 派生索引 | SQLite 与全文检索 | 变更监听、中文检索、重建一致性 |
| AI 接入 | Provider 适配层（API 服务、本地模型、CLI 环境） | 双入口统一抽象、密钥保护、失败回退、提示词模式管理 |
| 后续网页采集 | Defuddle、Turndown 等 | 正文提取质量、失败回退、来源保留 |
| 后续关系图 | Cytoscape.js 等 | 大图性能与实际使用价值 |

### 9.2 存储职责

推荐正文以本地 Markdown 文件保存；对象身份、类型和默认视图可以放入 Frontmatter。附件单独管理；来源摘录、精确锚点、ID 绑定等独有数据使用明确、可备份的持久化结构。SQLite 用于派生搜索和引用索引。

本地方案无需用户维护数据库服务器，但仍需要数据备份、索引维护和可靠写入。Web 存储与桌面文件不是同一份数据，后续若无同步功能，应明确提示数据彼此独立。

此项为 v1.0 已有的正确设计：Markdown 应尽可能成为知识原件，独有数据不能只保存在可删除的派生索引中。v1.1 保留并不因降低 MVP 工作量而删除。

### 9.3 实现前需要验证的风险

**最高优先风险（v1.1 提升）**：渲染文本选区与 Markdown 源位置的映射。用户在渲染后的页面选中一个词，系统必须准确找到 Markdown 原文中的那个位置，不能误改同名文本、代码或其他结构。这是整个项目最需要优先验证的技术点，建议作为 M0 的第一项验证目标。

其余需优先验证项：改名后的链接稳定性、跨文件保存中断恢复以及索引重建。复杂图数据库、向量数据库和服务端渲染不是当前 MVP 的必要前置条件。

### 10.1 核心验收清单

| 编号 | 操作与条件 | 通过标准 |
| --- | --- | --- |
| AC01 | 导入笔记后阅读选词，手动保存知识 | 原位链接与目标同时可用，重启后保持 |
| AC02 | AI 解释后编辑并保存 | 仅保存用户确认内容，并生成对应链接 |
| AC03 | 关闭网络或不配置 AI | 手动创建、阅读、搜索、建链仍可完成 |
| AC04 | 同一对象切换便签和页面 | ID、正文、来源及关系无变化 |

| AC12 | 删除目标或解除链接 | 不误删其他对象，缺失引用状态明确 |
| AC13 | 首次使用完整学习流程 | 见下方说明 |
| AC14 | 选词后选择“仅保存”而非建链 | 原文不被改写；知识对象已保存且可被引用；不出现“链接未完成”的失败提示 |

**AC13：首次使用完整学习流程（v1.1 新增）**

在全新安装、无任何已有知识库及 AI 配置的环境下，用户可以直接创建或导入 Markdown 笔记，选中陌生概念，自行填写知识内容，保存并形成可点击的 Wiki Link。

操作过程中，不要求用户理解 Markdown 双链语法、数据库、插件或文件索引概念。

如果用户选择启用 AI，则通过应用内统一入口完成配置并继续上述流程。

用这个用例衡量「开箱即用」，比单纯测量应用启动速度更有意义。AC13 与 8.5 的指标配套使用：AC13 判定流程能否完成，8.5 判定成本是否足够低。

### 10.2 发布条件

推荐以以上验收清单及 FR01 至 FR13 中的 P0 项为首版检查范围。目标平台实际安装、离线使用、真实文件持久化、数据恢复和主阅读流程都应验证，不能只依据界面原型或开发环境运行宣布完成。

所有造成数据丢失、静默覆盖、错误链接到另一对象或密钥进入导出包的问题均应在发布前解决。测试结果应记录版本、平台、样例知识库和已知限制。

### 12.2 对话方案的演变

早期提出 Next.js 方案，后期因桌面优先转向 React、Vite、Tauri 的候选组合；本文保留后期方向作为建议，不把两套架构同时列为强制要求。

早期将便签与短内容关联，用户随后明确纠正为自由选择展示形式；本文以用户的最终表述为准。早期计划较晚实现双向链接，后期讨论将 Wiki 链接和手动建链前移；本文据此安排 M2 先于 AI 集成。

来源区分、稳定 ID、本地 Markdown 加索引、原位改写和默认预览来自助理设计建议；保存一致性、失败恢复、量化性能目标及测试矩阵是本次补充规格。原对话中的交互示意不构成已实现或已验收的软件功能。
